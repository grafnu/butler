# Update Procedure for Butler Implementation Builds

This document outlines the standard procedure for pulling in specifications from `main` and ensuring implementations meet full spec compliance and stability.

## Coordinated Spec-First Agentic Workflow & Separation of Responsibilities

This project operates on a strict **spec-first development and testing** paradigm, where the primary objective is to evolve the core Butler specification into a robust, complete, and unambiguous definition of system behavior, rather than simply patching individual implementations.

The system defines a highly coordinated agentic workflow with a clean separation of responsibilities between two specialized roles:

1. **Verify & Update Spec (The Merger Agent - governed by `MERGER.md`):**
   - **Responsibility:** Strictly verifies spec-compliance across all cross-implementation pairs by executing integration tests. Does NOT make any code modifications or attempt to fix implementations.
   - **Feedback Loop to Implementations:** If an implementation is at fault, generates a `merge_analysis.md` file in the root of that implementation's repository describing the exact failures.
   - **Consuming Spec Feedback:** Reviews `spec_analysis.md` files generated by the Implementation Agents.
   - **Spec Evolution:** Clarifies specs under `spec/` or refines instructions in `UPDATE.md` to resolve issues cleanly.
   - **Artifacts:** Only specification/skill changes under `spec/` or `UPDATE.md`, `merge_analysis.md` feedback files, and the resolution of `spec_analysis.md` files are committed.

2. **Implement Spec (The Implementation Agent - governed by `UPDATE.md`):**
   - **Responsibility:** Modifies code inside its specific implementation directory (`butler/` and `bin/`) to satisfy the specification, resolving identified non-compliance, and raising spec-level feedback.
   - **Execution Loop:** Upon checkout, merges the latest specs from `main`, checks for `merge_analysis.md`, and audits specification files under `spec/`.
    - **Feedback Loop to Spec:** If a `spec_analysis.md` file is present, it MUST be analyzed to determine if any implementation updates are needed. If the listed issues have already been resolved (the problem is already fixed) or no implementation updates are required, the file MUST be removed immediately. The `spec_analysis.md` file should ONLY ever indicate active pending or required changes, never a historical log of what has been done. If a problem has already been fixed, it must be removed from the file. If new specific ambiguities, contradictions, omissions, or external spec incompatibilities prevent creating a compliant implementation, the Implementation Agent may create/update `spec_analysis.md` at the root of its implementation directory, ensuring it lists only unresolved, active issues.
   - **Code Refinement:** Refines the implementation logic until all requirements in `spec/` and all issues in `merge_analysis.md` are fully resolved and local tests pass, then deletes `merge_analysis.md` and commits/pushes.
   - **Spec Integrity:** Never modifies specifications or files outside of the allowed directories (`butler/`, `bin/`, and `UPDATE.md` if directed).
   - **Strict Isolation of Implementation Analysis:** To ensure independent design and prevent architectural pollution, the Implementation Agent MUST NOT inspect, read, search, or reference other Butler implementations in sibling directories (such as `impl/A/`, `impl/C/`, etc.), nor reference the internal code of the base UDMI repository. It MUST NOT base, guide, or inspire its implementation fixes on code written in other tracks. All compliance updates and bug fixes must be designed entirely independently, derived strictly and exclusively from THIS active implementation folder and the formal specification files under `spec/`.

Through this continuous feedback loop, the Butler specification is iteratively audited, streamlined, and hardened, achieving true specification-driven robustness.

## Pre-Requisites & Validation

1. **Branch Verification:**
   - This procedure MUST only be applied to branches that start with `impl_` (e.g., `impl_B`).
   - This procedure MUST NOT be performed on the `main` branch, or any other unrecognized branch.
   - Verify that the active git branch name is valid and the working directory is clean before beginning.

2. **Upstream Synchronization:**
   - Fetch the latest changes from the remote repository.
   - Merge `origin/main` into the current branch to pull in any specification updates.
   - *Conflict Resolution:* If merge conflicts occur within files in `spec/`, always auto-resolve them in favor of `origin/main` without exception, as specs on `main` are the immutable source of truth.

3. **UDMI Dependency Verification:**
   - Programmatically verify on startup that the local cloned `impl/udmi/` workspace is fully synchronized and pinned to the target specified in the authoritative `udmi_version.txt` file at the root of the workspace.
   - If out of sync, fetch and reset (via `git fetch --all --prune` and `git reset --hard`) inside `impl/udmi/` to guarantee alignment.

4. **Automatic Port Status Check:**
   - Prior to launching brokers or running tests, perform a socket-scanning pre-check to detect active processes on the branch-mapped MQTT/testing port (such as `45000-47999`) or standard etcd/MQTT ports.
   - If occupied, output the active process info and PID to `stderr` to assist in diagnosing conflicts, as specified in `spec/butler.md` Section 10.

## Code Compliance, Spec Auditing & Bidirectional Feedback (Meta-Auditor Loop)

This project utilizes a structured **Spec-Compliance Audit Loop** to guarantee full compliance with the authoritative specifications without maintaining brittle, duplicate parallel checklists.

### 1. Load and Parse the Compliance Matrix
The primary source of truth for all technical requirements is the **Compliance Matrix** natively defined in `spec/butler.md` (Section 13). 
- The agent must read and parse the entire compliance matrix from `spec/butler.md` on startup.
- If `merge_analysis.md` is present at the root, the agent must extract any requirement failures mentioned by the Merger Agent (referencing specific Requirement IDs like `REQ-CONN-001`, `REQ-HSK-002`, etc.).

### 2. Codebase Mapping
The agent must systematically scan the local codebase (specifically `butler/` and `bin/`) and map each Requirement ID from the Compliance Matrix to the specific files, classes, or functions implementing that behavior.

### 3. Verification Audit
For each Requirement ID, the agent must perform a rigorous code and behavioral audit:
- Verify that the local implementation fully satisfies the description and verifiable assertion stated in the Compliance Matrix.
- If any requirement is violated or partially implemented, update the code in `butler/` or `bin/` to ensure absolute alignment.
- Verify that unit and integration tests output compliance assertions and error messages directly referencing the failing Requirement ID (e.g. `[REQ-HSK-002]` or `[REQ-LOG-001]`) to maintain complete traceability.

### 4. Bidirectional Feedback & Fast-Failure
- **Specification Feedback:** If a `spec_analysis.md` file is present, it MUST be actively analyzed to see if any implementation update needs to be made. If the problems listed in `spec_analysis.md` have already been fixed or no implementation updates are required, the file MUST be removed immediately. The `spec_analysis.md` file MUST ONLY ever indicate pending or required changes, never a history of what has been done. If any requirement in the matrix is identified as ambiguous, contradictory, or impossible to implement due to external defects or immutable repository constraints, document only the active finding in `spec_analysis.md` and halt.
- **Clean Compliance State:** If all requirements are verified to be fully and cleanly satisfied, delete any existing `spec_analysis.md` file.
- **Merger Sign-off:** Once all failures documented in `merge_analysis.md` are resolved and verified to pass local tests, delete `merge_analysis.md` to signal readiness for re-verification.

## Verification & Testing Workflow

Before finishing, the implementation MUST be verified to prevent regressions:

1. **Environment Setup & Verification:**
   - **Automatic Validation:** Symmetrically validate and prepare the environment (virtualenv activation, dependency installation from `butler/requirements.txt`) before execution.
   - **Compliance with Testing Specs:** All local workspace environment initialization, isolated site model cloning, local service execution, and broker starting/stopping MUST natively comply with the requirements defined in `spec/butler.md` Section 10.
   - **No Sudo/No Privilege Elevation:** All tools and background processes MUST run entirely in non-privileged (no-sudo) user-space. Any requirement for `sudo` or administrative privilege elevation is a fundamental compatibility error. <!-- ASSUMPTION: The non-privileged pathway is automatically triggered purely by the presence of an explicit, custom MQTT port specification in the connection specification. --> The non-privileged pathway MUST be automatically triggered purely by the presence of an explicit, custom MQTT port specification in the connection specification.
   - **Opaque "Black-Box" Tooling:** All dependencies and scripts inside `impl/udmi` MUST be treated as black boxes. Do not attempt to analyze, patch, or work around their internal logic.
   - **Hermetic Isolation:** Ensure that there is no sharing of default ports, and that all runtime-created folders and logs are nested exclusively inside git-ignored locations (`tmp/`, `testing/`, or `logs/`).

2. **Execute Tests:**
   - Run any configured static analysis, linters, or standard unit tests to verify code health.
   - Run the automated, non-interactive integration smoke tests (`bin/smokeit`) to verify the complete registration, update, and failure rollback logic.
   - **Iterative and Fail-Fast Troubleshooting Policy:**
     - **Functional Issues:** If a failure is related to functional correctness or compliance with the application logic (e.g., implementing/refining the Butler state machine under `butler/` or `bin/`, resolving specification requirement discrepancies, or fixing test assertion bugs), the agent may continue to iteratively diagnose, apply bug fixes, and re-run local tests until they pass.
     - **Core System and Infrastructure Issues:** If a failure is a core system or environment issue (e.g., failing to connect to or start the base infrastructure, socket/port binding conflicts, failure to launch required system-wide background daemons like MQTT brokers, influx, or etcd, or executing standard platform utilities), the agent MUST NOT attempt to repair or retry the setup cycle more than 3 times. If these core system/infrastructure errors are not successfully resolved after at most 3 attempts, the agent MUST immediately cease execution, report a fatal system error, and hard-fail.

## File and Workspace Integrity Audit

1. **Strict File Restrictions:**
   - The *only* allowed changes in the repository at the end of the run are to files in `butler/` and `bin/`, the removal/update of `merge_analysis.md`, the creation, update, or removal of `spec_analysis.md`, and changes to `UPDATE.md` itself when explicitly directed.
   - No other stray files or changes (including `.gitignore`, `AGENTS.md`, `WORKFLOW.md`, `spec/`) are allowed. All temporary test logs or virtualenv directories MUST be nested within git-ignored locations and NOT committed.

2. **Commit and Push Procedure:**
   - Stage and commit only the allowed changed files (do not use global or untargeted add commands unprompted).
   - If no functional code changes were required to comply with the specs, create an empty commit with a simple "No changes required" message in the git commit log to signal a successful run.
   - If changes were made use a clear concise commit message explaining the updates. Do not describe what tests or checks were performed.
   - Push the committed branch to the remote repository.

## Testing Encountered Issues

1. **Empirical Specification and Tooling Defects:**
   - If a hard constraint or system utility in the immutable `impl/udmi` repository is logically or structurally broken (such as `reset_config` parsing errors or path resolution bugs), the Implementation Agent MUST NOT implement hacky workarounds or custom helper wrappers to hide the defect.
   - Instead, the agent MUST immediately declare that the constraints are impossible to achieve and output a hard error: "the UDMI spec is broken and the system will not work as intended until that is fixed."
   - State strictly empirical runtime findings resulting from bad specifications, rather than implementation bugs.

2. **Prohibition of Tool and Harness Modifications:**
   - Under no circumstances shall any agent attempt to modify, patch, or alter command options, flags, or parameters within the parent workspace harness scripts (such as `tools/run_updates`, `tools/run_cross`, or `tools/run_merger`), or tamper with core `gemini` command options (such as the `--proxy` or `--approval-mode` flags).
   - If the basic platform tools, system utilities, network options, or test runners fail to execute or connect due to environmental constraints, the agent MUST NOT attempt to patch or fix the runners. Instead, the agent MUST immediately raise a hard, fatal failure and exit.

3. **Immediate Hard Fail on Environment, Shared Library, and Binary Wrapper Errors:**
   - Under no circumstances shall an agent attempt to diagnose, debug, or work around low-level system or environment failures—such as missing shared libraries (`LD_LIBRARY_PATH`, `libdlt.so.2`), binary linkage errors, corrupted line endings in platform utilities, or kernel execution failures.
   - Creating, patching, or modifying binary wrappers, executable shell mocks (such as replacing platform binaries like `bin/mosquitto` with shell scripts), or manipulating `LD_LIBRARY_PATH` environment variables is strictly prohibited.
   - If any system utility or background daemon fails to launch due to low-level system or environment errors, the agent MUST NOT spend turns attempting to diagnose or patch the environment. The agent MUST immediately abort execution and exit with a hard failure: `"System/Environment Failure: Environment dependency error encountered: <error>"`.

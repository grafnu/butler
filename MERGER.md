# Instructions for Static Merge Analysis & Specification Refinement (MERGER.md)

This file governs the **Specification Merge** phase of the development lifecycle. This phase is executed strictly *after* a cross-implementation verification run (via `tools/run_cross`) has been completed. 

The primary goal of this phase is to consume the static evidence generated by the cross run, analyze implementation behaviors and discrepancies, resolve specification ambiguities or gaps, and refine the formal specifications.

---

## 1. Prerequisites and Sequence

The spec-driven development and verification pipeline operates in a strict sequence:
1. **tools/run_updates**: Automatically builds and synchronizes all implementation branches with the core specification.
2. **tools/run_cross**: Executes the live cross-implementation test matrix, generating static execution logs, test summaries, and diagnostics.
3. **tools/run_merger** (this file): Performs a purely static, offline analysis of the outputs from the cross run, updating specifications and guidelines in place.

---

## 2. Merger Agent Static Analysis Role & Core Goals

The role of the Merger Agent (governed by this `MERGER.md` skill) is strictly analytical and static. It operates after the cross-test run has completed.

### Core Directives:
1. **NO Live Execution:** The Merger Agent **MUST NOT** execute, compile, build, start, or run any of the implementations, local brokers, or live testing harnesses. It is a purely offline static analysis phase.
2. **NO Push to Git:** Under no circumstances should the Merger Agent push any changes to git. All proposals must be left in the active working branch for human review and validation.
3. **Static Evidence Analysis:** The Merger Agent must consume and analyze:
   - Recent git changes/diffs across the workspace.
   - Already existing static log files (such as `impl/*.log` or `out/*.log` generated by `tools/run_cross`).
   - Already existing test summary files (specifically `impl/test_summary.txt`).
   - Already existing feedback files (such as `_analysis.md` files, `spec_analysis.md`, or `merge_analysis.md` in implementation directories).
4. **Spec & Skill Evolution:** The primary output of the Merger Agent is updating the `.md` specification files (under `spec/`, e.g., `spec/butler.md`) and core workspace skill/configuration files (such as `UPDATE.md`) to resolve ambiguities, contradictions, or gaps highlighted by the static analysis.

---

## 3. Systematic Analysis & Specification Refinement Workflow

The Merger Agent must perform the static analysis and refinement of the workspace files through the following steps:

### Step 1: Audit Static Input Sources
- Read and inspect `impl/test_summary.txt` to identify which cross-implementation pairs succeeded or failed (`PASS`/`FAIL`).
- Locate and read the relevant log files (e.g., `impl/logs/*.log`, `out/*.log`) for any failing pairs to pinpoint the behavioral discrepancies.
- Check each implementation directory (e.g., `impl/{ID}/`) for any `spec_analysis.md` files generated by the Implementation Agents. These files describe precise spec ambiguities or incompatibilities.
- Review recent git diffs across implementation folders to see how individual implementations resolved issues.

### Step 2: Identify Ambiguities and Contradictions
Analyze the collected static data against the existing specifications in the `spec/` directory. Look for:
- Gaps in the specification that allowed implementations to diverge behaviorally.
- Redundant or multi-path requirements where a single, unified standard is required.
- Incompatible assumptions about data payloads, handshakes, or message topic formatting.

### Step 3: Update Specifications, Skill Files, and Propose Upstream Fixes
Translate the analytical findings directly into explicit, rigorous, and authoritative requirements:
- **Upstream Spec Proposals:** If the root cause of an ambiguity stems from generic or incomplete language in the foundational UUFI specification (`impl/udmi/docs/specs/uufi.md`), clearly document what needs to change in `uufi.md` in a dedicated `uufi_analysis.md` file at the root of the parent workspace. **Do not attempt to modify `uufi.md` directly**, as `impl/udmi` is immutable.
- **Local Spec Updates:** Update the local `.md` files under `spec/` (such as `spec/butler.md`) strictly to clarify rules specific to Butler application logic. Ensure all updates preserve and clarify the core interoperability standards defined in `spec/butler.md` Section 12, avoiding redundant rules or custom layouts.
- **Skill Updates:** Update `UPDATE.md` to guide Implementation Agents on how to handle the clarified rules and avoid repeating non-compliance patterns.

### Step 4: Write Implementation Feedback (`merge_analysis.md`)
For each implementation directory `impl/{ID}/`, the Merger Agent MUST:
1. **For failing implementations:** Create or update a `merge_analysis.md` file at the root of that implementation's repository (`impl/{ID}/merge_analysis.md`). This file MUST contain a precise, actionable diagnostic report describing the exact cross-implementation failures and non-compliance uncovered during testing, referencing specific log evidence and spec sections.
2. **For passing implementations:** If an implementation had no failures but a `merge_analysis.md` file exists from a previous run, remove it.
3. **Processing error handling:** If a `spec_analysis.md` file contains `"PROCESSING ERROR"`, do not interpret it as a spec-level issue. Note the implementation as having a processing failure and skip spec analysis for that implementation.

---

## 4. Workspace Cleanliness & Traceability

- Ensure that any updated `.md` files (specifications under `spec/` and skills like `UPDATE.md`) are formatted perfectly, idiomatic, and highly readable.
- Do not generate any stray files or temporary diagnostics outside of ignored paths (such as `tmp/`, `out/`, or `logs/`).
- Leave all modified files staged or unstaged in the active working branch without creating commits or pushing to remote origin, keeping the branch ready for human inspection.
